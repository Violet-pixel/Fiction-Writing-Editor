Visão geral

O Serifa guarda somente o que a pessoa escreve (projetos, capítulos, notas e revisões) e as preferências do editor. As mesmas entidades existem em dois lugares, conforme a maneira de abrir o programa:

Como o Serifa foi abertoOnde os dados ficamQuem grava
Site no GitHub PagesIndexedDB do navegador (banco serifa)O próprio editor, em JavaScript
visualizar.bat (servidor local pelo PowerShell)IndexedDB do navegador (banco serifa)O próprio editor, em JavaScript
Servidor Java com a APIPostgreSQL, ou arquivos JSON em SERIFA_DATA quando não há banco configuradoA API (/api/v1/projects)

Por que PostgreSQL no modo servidor

  • Transações de verdade. Salvar um projeto troca o projeto, os capítulos e grava uma revisão numa única transação: ou tudo entra, ou nada entra. Nunca fica um capítulo pela metade.
  • Regras no próprio banco. Chaves estrangeiras, CHECK e índices únicos barram dados inválidos mesmo que um cliente com defeito tente gravá-los.
  • Texto longo e JSON nativos. text guarda capítulos inteiros sem limite prático e jsonb guarda o documento .serifa de cada revisão já validado e consultável.
  • Backup simples. pg_dump gera uma cópia consistente com o servidor ligado (capítulo 9).
  • Sem dependência de compilação. O servidor carrega o driver JDBC por reflexão; sem SERIFA_DB_URL, ele usa arquivos JSON e funciona do mesmo jeito.

Por que IndexedDB no navegador

No GitHub Pages e no visualizar.bat não há servidor de aplicação: só arquivos estáticos. O IndexedDB é o banco que todo navegador moderno já traz, por isso o Serifa funciona sem instalar nada:

  • guarda centenas de megabytes (bem mais que o localStorage), suficiente para muitos livros e revisões;
  • é transacional e assíncrono: o salvamento automático não trava a digitação;
  • tem índices (projetoId) para listar os capítulos e as revisões de um projeto sem ler tudo;
  • os dados ficam no computador, presos à origem do site; nada é enviado para a internet.
Importante. Cada origem tem o seu próprio IndexedDB. O que foi escrito no site do GitHub Pages não aparece no visualizar.bat (que abre em http://localhost) e vice-versa. Para levar um projeto de um para o outro, use Arquivo › Salvar como (.serifa) e Arquivo › Abrir.

Modo servidor sem PostgreSQL

Quando SERIFA_DB_URL não está definida, o servidor Java grava cada projeto como um arquivo JSON (o mesmo formato .serifa) na pasta SERIFA_DATA (padrão ./dados-servidor), com gravação atômica: escreve num arquivo temporário e só depois troca pelo definitivo. As revisões ficam numa subpasta por projeto, com o mesmo limite de 50. As regras deste documento valem para os dois modos; o PostgreSQL acrescenta as garantias do próprio banco.

Regras e convenções

Convenções do modelo

  • Nomes em português, snake_case e no singular: capitulo, sessao_escrita, atualizado_em.
  • uuid para o que nasce no navegador (projeto, capitulo): o editor cria o identificador sem falar com o servidor, então um projeto feito no GitHub Pages pode ser enviado para a API mais tarde sem trocar de id.
  • bigserial para registros auxiliares (revisões, sessões, exportações, dicionário).
  • Datas sempre em timestamptz (UTC no banco; o editor mostra no fuso local). Para agrupar por dia, use inicio::date (ou inicio AT TIME ZONE 'America/Sao_Paulo').
  • Valores fixos com CHECK em vez de tipos ENUM: adicionar um formato novo é só trocar a restrição, sem migração de tipo.
  • Os mesmos valores do arquivo .serifa: rascunho, revisao, pronto; livro, wattpad, ao3; a4, livro-6x9 etc.

Exclusões em cascata

Apagar um projeto (DELETE /api/v1/projects/{id} ou Excluir projeto na lista de projetos) remove tudo o que é dele. Apagar um capítulo mantém as sessões e exportações, com capitulo_id nulo (ON DELETE SET NULL).

Vínculos preservados. A cada salvamento, o servidor atualiza os capítulos no lugar (INSERT ... ON CONFLICT (id) DO UPDATE) e apaga só os que saíram do projeto, então sessões e exportações continuam ligadas aos capítulos que ainda existem.

Validação antes de gravar

  1. A API confere o corpo: JSON válido, até 10 MB, format = "serifa" e version = 1.
  2. O HTML de cada capítulo passa pelo sanitizador (só os blocos e marcações da especificação; nada de script, eventos on* ou links javascript:).
  3. A contagem de palavras usa o mesmo contador do editor, que dá o mesmo resultado em JavaScript, Java e C.
  4. Só então abre a transação, grava e cria a revisão (capítulo 6).

Conforme server/src/main/resources/db/schema.sql (PostgreSQL). Na coluna Nulo, "sim" indica que o campo aceita NULL. Todas as tabelas são criadas com CREATE TABLE IF NOT EXISTS, então o arquivo pode ser aplicado de novo sem erro.

Abertura e atualização do banco

const req = indexedDB.open('serifa', 1);
req.onupgradeneeded = () => {
  const db = req.result;
  db.createObjectStore('projetos', { keyPath: 'id' });
  db.createObjectStore('capitulos', { keyPath: 'id' }).createIndex('projetoId', 'projetoId');
  db.createObjectStore('revisoes', { keyPath: 'id', autoIncrement: true }).createIndex('projetoId', 'projetoId');
  db.createObjectStore('dicionario', { keyPath: 'palavra' });
  db.createObjectStore('sessoes', { keyPath: 'dia' });
  db.createObjectStore('preferencias', { keyPath: 'chave' });
};
  • Salvar um projeto usa uma transação readwrite sobre projetos, capitulos e revisoes: os três mudam juntos ou nenhum muda.
  • Uma versão nova do banco (2, 3...) só acrescenta stores e índices dentro de onupgradeneeded; dados existentes nunca são apagados na atualização.
  • Se o navegador bloquear o IndexedDB (janela anônima de alguns navegadores), o editor passa a trabalhar só na memória: nesse caso, salve o .serifa antes de fechar.

Versões e revisões

Cada salvamento guarda uma revisão

Ao salvar (Ctrl+S, salvamento automático ou PUT /api/v1/projects/{id}), o Serifa grava o projeto e, na mesma transação, uma linha em revisao com o documento .serifa completo. São mantidas as 50 revisões mais recentes de cada projeto; as mais antigas são apagadas no mesmo salvamento.

  1. Confere a versao esperada (capítulo 7) e incrementa projeto.versao.
  2. Grava projeto (INSERT ... ON CONFLICT (id) DO UPDATE), atualiza os capítulos no lugar (ON CONFLICT (id) DO UPDATE) e apaga só os que saíram.
  3. Insere a revisão com o próximo numero do projeto (maior número + 1).
  4. Apaga o que passou de 50 e faz o COMMIT.
-- poda: mantém só as 50 revisões mais novas do projeto
DELETE FROM revisao
 WHERE projeto_id = $1
   AND numero <= (SELECT max(numero) FROM revisao
                    WHERE projeto_id = $1) - 50;

O texto é gravado no navegador enquanto você escreve. Para não encher o histórico com revisões quase iguais, a revisão automática é criada no máximo uma vez a cada 5 minutos de digitação; Ctrl+S sempre cria uma. No navegador, a poda das 50 mais recentes é feita logo depois de gravar a revisão nova.

Restaurar uma revisão

  1. Abra Arquivo › Revisões (ou GET /api/v1/projects/{id}/revisions).
  2. Escolha a revisão pela data e pelo total de palavras.
  3. Clique em Restaurar. O projeto atual não é perdido: a restauração é um salvamento novo (com o próximo numero) e a versão anterior continua no histórico.

Concorrência otimista

O mesmo projeto pode estar aberto em duas abas ou em dois computadores ligados ao mesmo servidor. Para que um não apague o trabalho do outro sem aviso, cada gravação diz qual versao ela leu. O banco só aceita se ninguém salvou no meio do caminho. A coluna versao já vem no schema.sql.

UPDATE projeto
   SET titulo = $2, ..., versao = versao + 1, atualizado_em = now()
 WHERE id = $1
   AND versao = $3          -- versão que o editor leu
RETURNING versao;

-- na gravação com upsert, a mesma condição vai no DO UPDATE:
INSERT INTO projeto (id, titulo, autor, idioma, documento, versao)
VALUES ($1, $2, $3, $4, $5::jsonb, 1)
ON CONFLICT (id) DO UPDATE
   SET titulo = EXCLUDED.titulo, documento = EXCLUDED.documento,
       versao = projeto.versao + 1, atualizado_em = now()
 WHERE projeto.versao = $6
RETURNING versao;
SituaçãoResultado
Ninguém salvou desde a leitura1 linha atualizada; a API responde 200 com a versao nova
Outra aba ou pessoa salvou antes0 linhas; ROLLBACK e a API responde 409 Conflict com a versão atual
Projeto foi apagado0 linhas e o projeto não existe: 404

O que o editor faz num conflito

  1. Mostra o aviso "Este projeto foi alterado em outro lugar".
  2. Não sobrescreve nada: o texto continua salvo no navegador e a pessoa escolhe recarregar a versão mais nova ou salvar a sua como cópia (Salvar como). A versão de cada lado continua nas revisões.

No navegador o mesmo campo versao fica no store projetos: a transação do IndexedDB lê o registro, compara a versão e grava no mesmo passo, o que protege contra duas abas abertas no mesmo projeto.

Consultas prontas

Para rodar no psql ou em qualquer cliente PostgreSQL. Troque :'projeto' pelo id do projeto (no psql: \set projeto '...').

Palavras por dia

SELECT s.inicio::date AS dia,
       SUM(GREATEST(s.palavras_fim - s.palavras_inicio, 0)) AS palavras,
       MAX(p.meta_diaria) AS meta,
       SUM(GREATEST(s.palavras_fim - s.palavras_inicio, 0)) >= MAX(p.meta_diaria) AS meta_batida
  FROM sessao_escrita s
  JOIN projeto p ON p.id = s.projeto_id
 WHERE s.projeto_id = :'projeto'
   AND s.inicio >= current_date - 30
 GROUP BY 1
 ORDER BY 1;

Capítulos por status

SELECT status, COUNT(*) AS capitulos, SUM(palavras) AS palavras
  FROM capitulo
 WHERE projeto_id = :'projeto'
 GROUP BY status
 ORDER BY array_position(ARRAY['rascunho','revisao','pronto'], status);

Últimas revisões

SELECT numero, criado_em,
       documento ->> 'title'                     AS titulo,
       jsonb_array_length(documento -> 'chapters') AS capitulos,
       tamanho
  FROM revisao
 WHERE projeto_id = :'projeto'
 ORDER BY numero DESC
 LIMIT 10;

Exportações por formato

SELECT formato, COUNT(*) AS vezes,
       pg_size_pretty(SUM(tamanho)::bigint) AS volume,
       MAX(criado_em) AS ultima
  FROM exportacao
 WHERE criado_em >= now() - interval '90 days'
 GROUP BY formato
 ORDER BY vezes DESC;

Projetos recentes com total de palavras

SELECT p.titulo, p.modo_formato, p.atualizado_em,
       COUNT(c.id) AS capitulos, COALESCE(SUM(c.palavras), 0) AS palavras
  FROM projeto p
  LEFT JOIN capitulo c ON c.projeto_id = p.id
 GROUP BY p.id
 ORDER BY p.atualizado_em DESC
 LIMIT 20;

Backup e restauração

Modo servidor: pg_dump

  1. Gere a cópia com o servidor ligado (o pg_dump lê um retrato consistente): 
    pg_dump -h localhost -U serifa -d serifa -F c -f serifa-2026-10-28.dump
  2. Guarde o arquivo .dump fora do computador (pen drive, nuvem pessoal). Ele contém os textos.
  3. Para restaurar num banco vazio: 
    createdb -h localhost -U postgres -O serifa serifa
pg_restore -h localhost -U serifa -d serifa --no-owner serifa-2026-10-28.dump
  4. Ligue o servidor e confira http://127.0.0.1:8080/api/v1/health.
Rotina sugerida. Um pg_dump por dia (Agendador de Tarefas do Windows ou cron), guardando os últimos 14. No modo arquivos JSON, basta copiar a pasta SERIFA_DATA.

Qualquer modo: exportar .serifa

O arquivo .serifa é o backup mais simples e funciona em qualquer maneira de abrir o Serifa:

  1. No editor, Arquivo › Salvar como (Ctrl+Shift+S) e escolha a pasta. No Chrome e no Edge, os próximos Ctrl+S gravam no mesmo arquivo.
  2. Para restaurar, Arquivo › Abrir (Ctrl+O) e escolha o .serifa. Se já existir um projeto com o mesmo id, o Serifa pergunta se substitui ou abre como cópia.
  3. Pela API: GET /api/v1/projects/{id} devolve o .serifa; POST /api/v1/projects com o arquivo no corpo importa (e já grava a primeira revisão).

O .serifa leva capítulos, notas, configurações, dicionário do projeto e ideias ignoradas. Não leva as revisões antigas nem as sessões de escrita.

Proteções no servidor

  • O servidor escuta só em 127.0.0.1 por padrão; para abrir na rede é preciso configurar de propósito.
  • Todas as consultas usam PreparedStatement com parâmetros (nada de SQL montado com texto do usuário).
  • Corpo das requisições limitado a 10 MB; HTML sanitizado antes de gravar (capítulo 3).
  • Cabeçalhos de segurança: Content-Security-Policy, X-Content-Type-Options: nosniff, X-Frame-Options: DENY e Referrer-Policy.
  • A senha do banco vem de variável de ambiente (SERIFA_DB_PASSWORD) e nunca aparece em log.

Preparar o PostgreSQL

Só é necessário para o modo servidor com banco. O site e o visualizar.bat não usam PostgreSQL.

  1. Instale o PostgreSQL 15 ou mais novo (no Windows, pelo instalador oficial; no Linux, pelo gerenciador de pacotes). Anote a senha do usuário postgres.
  2. Crie o usuário e o banco do Serifa: 
    psql -h localhost -U postgres -c "CREATE ROLE serifa LOGIN PASSWORD 'troque-esta-senha';"
psql -h localhost -U postgres -c "CREATE DATABASE serifa OWNER serifa;"
  3. Aplique o esquema (na raiz do projeto): 
    psql -h localhost -U serifa -d serifa -f server/src/main/resources/db/schema.sql
  4. Baixe o driver JDBC do PostgreSQL (postgresql-42.x.jar) e deixe-o numa pasta conhecida, por exemplo server/lib/. O servidor não depende dele para compilar.
  5. Defina as variáveis de ambiente (tabela abaixo) no terminal em que o servidor vai rodar.
  6. Compile e inicie o servidor com o driver no classpath (bash server/build.sh ou server\build.cmd antes): 
    java -cp "server/target/serifa.jar:server/lib/postgresql-42.x.jar" serifa.cli.Main serve
rem no Windows o separador é ponto e vírgula:
java -cp "server\target\serifa.jar;server\lib\postgresql-42.x.jar" serifa.cli.Main serve
  7. Confira http://127.0.0.1:8080/api/v1/health: deve responder {"status":"ok","app":"Serifa",...}.
